# epScript는 트리거 용량을 어떻게 아끼는가, 그리고 새 Lua 문법 에디터 설계

목적: **트리거 용량(개수·바이트) 절약.** 실행 속도가 아니라 맵에 실리는 트리거 데이터 크기를 줄이는
장치를 다룬다. 앞선 문서: [MSQC_INTERNALS.md](MSQC_INTERNALS.md),
[MSQC_CTRIGASM_FEASIBILITY.md](MSQC_CTRIGASM_FEASIBILITY.md).

조사 대상: epScript 변환기 소스(`~/.eudplib-linux/src/epscript-patched/parser/epparser.lemon`,
1,711줄), eudplib 0.80.6(`core/allocator`, Rust `rust/src/allocator/payload.rs`, `core/variable`,
`ctrlstru`, `maprw/inlinecode`), 그리고 아래 실측(2026-09-11, 같은 venv에서 합성 트리거를 100개와
200개 만들어 페이로드 크기 차이를 나눈 값).

---

## 0. 결론

1. **epScript 자체는 트리거를 하나도 최적화하지 않는다.** 문법을 eudplib 호출로 1:1 바꾸는
   변환기일 뿐이다(1절 표). 용량 절약은 전부 eudplib 백엔드의 일이다.
2. eudplib의 절약 장치 중 가장 큰 것은 **트리거 겹쳐 쌓기(object stacking)** 다. 트리거는
   2408바이트가 아니라 조건·액션 수에 따라 **146~1040바이트**로 실린다(2.1절 실측). 그다음이
   변수 72바이트·점프 항목 20바이트·라이트 변수 0바이트, 그다음이 액션 64개 패킹과 SeqCompute 중복
   제거, 함수 1회 방출이다.
3. CtrigAsm/TEP 세계는 이 장치를 **하나도 못 쓴다.** tepc가 낸 `TRIGP*.chk` 를 어셈블러 플러그인이
   `Db`로 통째로 페이로드에 복사하므로 트리거 하나가 항상 2400바이트다. `CVariable` 하나도
   2400바이트다(3절).
4. 따라서 "새 문법의 Lua 맵 에디터"로 용량을 아끼려면 **백엔드를 eudplib로 두는 것**이 핵심이고
   문법은 부차적이다. epScript와 같은 구조(프런트엔드 → eudplib)를 취하되, 프런트엔드를 C++ 대신
   파이썬에 두고 eudplib을 직접 호출하는 것이 가장 싸다(4절). epScript가 놓치는 용량 지점 8가지를
   문법에서 잡을 수 있다(4.2절).
5. 새 언어 없이도 되는 대안이 하나 있다. 어셈블러 플러그인을 포크해 `TRIGP` 트리거를 `Db`가 아니라
   `RawTrigger(trigSection=...)` 객체로 실으면 기존 CtrigAsm 코드가 그대로 겹쳐 쌓인다(5절).
   조건이 붙지만 가장 빨리 효과를 보는 길이다.

## 1. epScript는 무엇을 하고 무엇을 안 하는가

`epparser.lemon`의 문법 액션은 파이썬 소스 문자열을 찍어낼 뿐이다. 대응표:

| epScript 문법 | 방출되는 eudplib 코드 | 용량 의미 |
| --- | --- | --- |
| `var a;` / `var a, b;` | `a = EUDVariable()` / `EUDCreateVariables(2)` | 변수 = 72바이트 vtable 트리거 |
| `var a: EUDLightVariable = 0;` | 타입 지정 변수 | 4바이트 `Db` (실측 0바이트, 다른 객체 틈에 들어감) |
| `const X = 식;` | `X = _CGFW(lambda: [식], 1)[0]` | 컴파일 타임 상수, 트리거 0 |
| `a = 식;` | `a << (식)` | `SeqCompute` 1회 |
| `a, b = x, y;` | `_SV([a, b], [x, y])` | `SetVariables` → 한 트리거에 묶음 |
| `a += b;` / `a++;` | `a.__iadd__(b)` | `SeqCompute` |
| `if (c) {}` / `else if` / `else` | `EUDIf()(c)` / `EUDElseIf()` / `EUDElse()` | 조건당 트리거 2개(2.6절) |
| `c1 && c2` / `c1 \|\| c2` | `EUDSCAnd()(c1)(c2)()` / `EUDSCOr` | 단락 평가 → 피연산자마다 트리거 추가 |
| `while (c) {}` / `for (i;c;s) {}` | `EUDWhile()(c)` + `EUDSetContinuePoint()` | 트리거 2개 + 점프 |
| `switch (v) { case n: }` | `EUDSwitch(v)` / `EUDSwitchCase()(n)` | 이진 탐색 + 점프 테이블(항목 20바이트) |
| `break` / `continue` / `return` | `EUDBreak()` / `EUDContinue()` / `EUDReturn()` | 점프 |
| `function f(a) {}` | `@EUDFunc def f(a):` | 본문 1회, 호출 지점 트리거 1개 |
| `function f(a: TrgUnit)` | `@EUDTypedFunc([TrgUnit])` | 같음 |
| `object O { function m() {} }` | `class O(EUDStruct):` + `@EUDMethod` | 구조체 |
| `arr[i]` / `o.x` | `_ARRC` / `_ATTC` (읽기), `_ARRW` / `_ATTW` (쓰기) | 배열 접근 |
| `f(x)` 반환값 받기 | `_SRET(f(x), [..])` | 반환 변수 |

여기에 최적화 패스는 없다. 상수 접기도 파이썬이 `_CGFW` 람다를 평가하면서 얻는 부수 효과이고,
`if` 조건의 상수 비교가 한 트리거의 조건으로 합쳐지는 것도 eudplib `EUDIf`의 일이다.

## 2. eudplib이 용량을 아끼는 장치 (영향 큰 순)

### 2.1 트리거 겹쳐 쌓기 — `stack_objects` (Rust `payload.rs` 174행)

트리거 구조체 2408바이트 중 게임이 실제로 읽는 dword는 정해져 있다: `prevptr`, `nextptr`, 사용한
조건 각 5dword, "조건 끝" 표시 5dword, 사용한 액션 각 8dword, "액션 끝" 표시 8dword, 플래그 1dword,
마지막 바이트(`currentAction`). `pbuffer.rs`의 `_write_trigger`는 이 자리만 "점유"로 표시하고
나머지는 `WriteSpace`(비점유)로 둔다. `stack_objects`는 객체마다 점유 지도를 받아, **앞선 객체들의
비점유 구멍에 들어맞는 가장 낮은 주소**에 놓는다(first-fit, 충돌 시 건너뛰기 표로 가속). 결과적으로
트리거들이 서로의 빈 공간에 끼어든다. `EUDLightVariable`의 4바이트 `Db`가 실측 0바이트인 이유도
이것이다.

실측(`CompressPayload(True)`, 이 eudplib에서는 `False`가 지원되지 않으므로 항상 켜져 있음):

| 조건 수 | 액션 수 | 트리거당 바이트 | 2408 대비 |
| --- | --- | --- | --- |
| 0 | 1 | 146 | 1/16 |
| 1 | 1 | 251 | 1/9.6 |
| 0 | 2 | 241 | 1/10 |
| 1 | 2 | 230 | 1/10 |
| 2 | 2 | 272 | 1/8.9 |
| 3 | 3 | 323 | 1/7.5 |
| 0 / 1 / 2 | 4 | 375 | 1/6.4 |
| 0 | 8 | 719 | 1/3.3 |
| 4 | 16 | 1040 | 1/2.3 |
| 0 / 8 | 32 | 2080 | 1/1.16 |
| 0 | 63 | (측정 실패: 할당기 인덱스 패닉) | — |

작은 트리거일수록 이득이 크고, 액션 32개를 넘으면 거의 이득이 없다. 즉 **"트리거 하나에 액션을
가득 채우기"와 "겹쳐 쌓기"는 서로 상쇄**하며, 용량 기준 최적점은 액션 4~8개짜리 트리거를 많이 만드는
쪽이 아니라 **필요한 액션만 담은 작은 트리거**다. 액션 64개 한도 채우기(2.3절)는 실행 횟수를 줄이는
장치지 바이트를 줄이는 장치가 아니다.

### 2.2 변수·점프·라이트 변수의 크기

| 객체 | 설계 | 실측 | 근거 |
| --- | --- | --- | --- |
| `EUDVariable` | 72바이트 간격 (vtable 트리거를 33개 겹침) | 144바이트/개 (합성 테스트, 구멍에 다른 객체 없음) | `vbuf.py` "72 bytes per variable" |
| 점프 테이블 항목 (`EUDSwitch`, 함수 포인터) | 20바이트 | — | `jumptable.py` "20 bytes per nextptr" |
| `EUDLightVariable` | 4바이트 `Db` | 0바이트 (틈에 흡수) | `eudlv.py` |
| `EUDLightBool` | 1비트 (32개가 dword 하나) | 0 | `eudlv.py` |

CtrigAsm의 `CVariable`은 TEP 트리거 하나 = 2400바이트다. 변수 100개면 240KB 대 7~14KB.

### 2.3 한 트리거에 조건 16·액션 64

`DoActions`/`RawTrigger`는 64액션까지 한 트리거에 담는다. 바이트로는 2.1절대로 상쇄되지만
**트리거 개수**(TEP 65,536 한도, 실행 횟수)는 줄어든다. CtrigAsm의 `DoActionsX`도 같은 일을 하므로
여기서는 차이가 없다.

### 2.4 SeqCompute / VProc — 액션 자체를 줄인다

변수 대입은 vtable의 dest·modifier 필드를 고쳐 쓰고 점프한다(앞 답변). `SeqCompute`는 같은 변수의
dest·modifier가 직전과 같으면 그 패치 액션을 **생략**하고, 상수 대입은 vtable 없이 `SetDeaths` 한
줄로 바꾸며, 61액션까지 한 트리거에 묶는다. CtrigAsm의 T/TT는 매번 3~5액션을 전부 내고 사전
트리거·마샬링 트리거로 흩뿌린다.

### 2.5 함수 — 본문 1회, 호출 지점 1트리거

`EUDFunc.__call__`(`eudfuncn.py` 211행): 호출 지점은 "복귀 주소 대입 + 반환 변수 dest 대입 + 상수
인자 대입"을 **트리거 하나**의 `SeqCompute`로 만들고 `SetNextTrigger(fstart)`로 점프한다. 변수 인자는
그 변수의 vtable 체인에 끼운다. 본문은 처음 호출될 때 한 번만 방출된다. CtrigAsm의 `f_` 계열은
Include 본문은 1회지만 호출 지점마다 입력 마샬링 트리거, 호출 트리거, 출력 트리거가 붙는다(각
2400바이트).

### 2.6 제어문 비용

`EUDBranch`(`trigger/branch.py`): 조건 트리거 하나(`nextptr = onfalse`, 참이면 자기 nextptr을
`tjtrg`로 바꿈) + 복원 트리거 하나(`nextptr = ontrue`, 자기를 되돌림). 즉 **`if` 하나 = 트리거 2개**,
조건 16개까지 그대로 한 트리거에 들어간다. `while`은 같은 2개 + 끝의 `SetNextTrigger`(트리거 아님).
`EUDSwitch`는 이진 탐색 트리거 + 점프 테이블(항목당 20바이트). `EUDSCAnd`/`Or`는 피연산자마다
분기·플래그 트리거가 붙는다. CtrigAsm의 `CIf`/`CWhile`/`CIfX`도 구조는 같고 개수도 비슷하다.

### 2.7 읽기 함수 공유

`memio/readtable.py`의 `consecutive_table`은 (마스크, 시프트) 조합마다 읽기 트리거 묶음을 **한 번만**
만들어 공유하고, `f_readgen_epd`는 `functools.cache`로 같은 마스크의 리더를 재사용한다. CtrigAsm의
`CRead`/`f_Read`도 Include로 1회 방출이라 차이는 호출 지점 비용(2.5절)에 있다.

### 2.8 클래식 TRIG 인라인·공유 — CtrigAsm 세계에서는 꺼져 있다

`maprw/inlinecode`는 맵의 TRIG 섹션 트리거를 페이로드 코드로 다시 짜고(`inline_codify_binary_trigger`),
여러 플레이어가 같은 트리거를 실행하면 하나로 공유하며(`try_share_trigger`), 그 결정에
`get_trigger_size`(위 겹쳐 쌓기와 같은 계산)를 쓴다. `PRT_SetInliningRate(rate)`가 비율을 정한다.
**`STRCtrig Assembler v5.5.py` 6행이 `PRT_SetInliningRate(0)`으로 이 기능을 끈다.** CtrigAsm 트리거는
`Label` 기반 자기수정이라 위치가 바뀌면 깨지기 때문이다.

## 3. CtrigAsm/TEP가 지금 내는 비용

| 항목 | CtrigAsm/TEP | eudplib |
| --- | --- | --- |
| 트리거 하나 | 2400바이트 고정. `TRIGP*.chk`를 `Db`로 복사 (`STRCtrig Assembler v5.5.py` 215행) | 146~2080바이트 (2.1절) |
| 변수 하나 | 2400바이트 (`CVariable` = 트리거 1개) | 72바이트 |
| 변수 대입 | T/TT 패치 3~5액션 + 사전 트리거 | `SeqCompute` 중복 제거 |
| 함수 호출 지점 | 마샬링 트리거 2~4개 | 트리거 1개 |
| 점프 테이블 | 트리거 1개/항목 | 20바이트/항목 |
| 클래식 TRIG 공유 | 꺼짐 (`PRT_SetInliningRate(0)`) | 켜짐 |

theSeed의 `TRIGP0.chk`가 465,600바이트 = 트리거 194개인데, 그 안의 트리거 대부분은 조건 0~3개,
액션 1~8개다. 같은 내용을 eudplib이 실었다면 2.1절 표로 볼 때 **대략 1/5~1/10** 이다. 정확한 수치는
5절 방식으로 실제 변환해 봐야 나온다.

## 4. 새 Lua 문법 에디터 설계 (목적: 용량)

### 4.1 아키텍처 선택지

| 선택지 | 구조 | 용량 효과 | 비용 | 판정 |
| --- | --- | --- | --- | --- |
| A. 파이썬 호스트 프런트엔드 | 새 문법 파서(파이썬, Lark 등) → AST → **eudplib 함수를 직접 호출** | eudplib 전부 | 파서 + 방출기. 코드 생성 텍스트 없음, 디버깅 쉬움 | **권장** |
| B. epScript 방식 | C++ lemon 파서 → 파이썬 소스 텍스트 → eudplib | 같음 | C++ 툴체인, 텍스트 생성 단계 | epScript 코드를 재활용할 때만 |
| C. Lua 호스트 | Lua로 쓴 컴파일러 → 파이썬 소스 텍스트 → eudplib | 같음 | 런타임 둘, 두 언어의 의미 차이를 문자열로 맞춤 | 기존 Lua 자산 재사용이 목적일 때 |
| D. CtrigAsm 백엔드 | 새 문법 → CtrigAsm Lua → tepc | **없음** (3절 비용 그대로) | 낮음 | 목적에 부적합 |

A를 권하는 이유: epScript가 파이썬 텍스트를 찍는 것은 변환기가 C++이라서다. 프런트엔드가 파이썬이면
AST를 걸으며 `EUDIf()`, `SeqCompute()`, `RawTrigger()`를 그 자리에서 부르면 된다. euddraft 플러그인
하나(`.eds`에 `[MyLang]` + 소스 경로)로 얹을 수 있어 기존 파이프라인(tepc → euddraft)과 공존한다.

### 4.2 문법이 용량을 좌우하는 지점 — epScript보다 나아질 수 있는 8가지

1. **조건 목록과 단락 평가를 구분.** `if a, b then` 은 조건 2개짜리 트리거 하나(2.6절), `if a and b then` 만
   `EUDSCAnd`. epScript는 `&&`가 항상 단락 평가라 트리거가 는다.
2. **`when c1, c2 do 액션 end`** — 분기 쌍 없이 `RawTrigger(conditions, actions)` 하나. 클래식 트리거의
   본래 형태이며 146~375바이트다. 맵 로직의 대다수가 이 형태다.
3. **변수 종류를 문법으로.** `var`(72바이트 vtable, 변수 간 대입 필요할 때), `light`(4바이트, 상수
   대입·조건 비교만), `flag`(1비트). epScript는 타입 지정을 해야 라이트 변수가 된다.
4. **`const`는 컴파일 타임.** 주소 산술(`EPD(x)+1`, `DtoA`)을 전부 파이썬에서 접는다. GOTCHAS 3·4절의
   "중간 연산자 첫 인자" 함정이 사라진다.
5. **`inline function`** (본문 복제, 호출 0) 과 **`function`** (본문 1회, 호출 1트리거)을 구분. 짧은
   함수는 inline이 작다.
6. **다중 대입을 한 문장으로.** `a, b, c = x, y, z` → `SetVariables` 한 번 → 트리거 하나.
7. **루프 펼치기 지시.** `for i = 0, 7 unroll do` 는 컴파일 타임 반복(플레이어별 unroll이 필요한
   `DtoA` 계열), 지시 없으면 `EUDWhile`.
8. **작은 트리거 선호.** 액션을 64개까지 억지로 합치지 말 것(2.1절). 방출기는 "한 문장 = 한 트리거"를
   기본으로 하고, 합치기는 실행 횟수가 문제일 때만 옵션으로.

### 4.3 문법 스케치

```lua
const BASE   = 0x58A364 + 4*12          -- 컴파일 타임
var   hp, mp = 100, 50                  -- EUDVariable ×2
light tick   = 0                        -- EUDLightVariable
flag  armed                             -- EUDLightBool

when Deaths(P1, AtLeast, 1, 0), NotTyping() do   -- RawTrigger 1개 (146~375B)
  SetDeaths(P1, Subtract, 1, 0)
  hp += 1                                          -- SeqCompute
end

if hp >= 10, mp >= 5 then                -- EUDIf, 조건 2개 한 트리거
  hp, mp = hp - 10, mp - 5               -- SetVariables 1회
elseif tick == 0 then
  ...
end

function heal(p, n)                      -- EUDFunc, 본문 1회
  SetDeaths(p, Add, n, 0)
end
inline function bump(v) v += 1 end       -- 호출 지점에 복제

for p = 0, 7 unroll do                   -- 컴파일 타임 반복
  when LocalPlayerID(p) do heal(p, 1) end
end

switch tick case 0 ... case 1 ... end    -- EUDSwitch, 항목 20B
```

파일 확장자·주석 규칙·문자열 처리(STRx 삽입은 eudplib `Db`/`EUDArray`가 담당)는 2차 문제다.

### 4.4 기존 CtrigAsm 자산

CAPlot/CSPlot, DisplayPrint, iStr 계열, TStruct 등은 Lua이고 TEP 트리거를 방출한다. 새 언어로
자동 변환되지 않는다. 두 가지 길:

- **FFI.** 새 언어에서 `python "eudplib 식"` 또는 `raw { 클래식 트리거 }` 를 허용한다(epScript의
  파이썬 임포트와 같은 발상). 급한 것은 이걸로 메우고, 자주 쓰는 것부터 포팅한다.
- **혼용.** 한 맵에서 tepc(CtrigAsm) 산출물과 새 언어 플러그인이 같이 돈다. 데이터 교환은
  Deaths/EPD 주소로 한다(MSQC의 `val` 채널과 같은 방식). 다만 CtrigAsm 쪽 트리거는 여전히
  2400바이트라 용량 이득은 새 언어로 옮긴 만큼만 난다.

### 4.5 단계

1. 파이썬 파서(Lark)로 4.3절의 `when`/`if`/`var`/`light`/`const`/`function`만 구현하고, 방출기가
   eudplib을 직접 호출하도록 만든다. 트리거 1~2개짜리 예제로 페이로드 크기를 2.1절 표와 대조한다.
2. euddraft 플러그인으로 포장해 `.eds` 한 줄로 켜지게 한다. tepc와 병행.
3. theSeed의 작은 모듈 하나(예: 키 입력 처리)를 옮겨 TRIG/페이로드 바이트를 전후 비교한다.
4. 4.2절 나머지(inline, unroll, switch)와 FFI.

## 5. 새 언어 없이 되는 대안 — 어셈블러 포크로 TRIGP 겹쳐 쌓기

`STRCtrig Assembler v5.5.py`가 `TRIGP*.chk`를 `Db`로 싣는 대신 2400바이트씩 잘라
`RawTrigger(trigSection=...)` 로 만들면(eudplib이 인라인 코드에 쓰는 바로 그 생성자) 기존 CtrigAsm
트리거가 그대로 2.1절의 겹쳐 쌓기를 받는다. 필요한 조건:

- **Label 해석을 컴파일 타임으로.** 지금은 맵 시작 시 STRX PATCH 루프가 2400바이트 간격으로 훑어
  `Label` 마커 조건(`0xFE000000` 등)을 찾는다. 겹쳐 쌓으면 간격이 일정하지 않으므로, 플러그인이
  TRIG를 파싱할 때 인덱스→트리거 객체 표를 만들고 `SetCtrigX` 계열 액션의 대상 주소를 eudplib
  `ConstExpr`로 바꿔 넣어야 한다. `Next1`/`Next2`(다음 트리거) 참조도 같은 표로 푼다.
- **자기수정 참조는 "점유된" 필드만.** `0x148/0x158/0x15C/0x160`(첫 액션의 마스크·dest·값·연산자)은
  액션이 있으면 점유 필드라 안전하다. 비어 있는 액션 슬롯이나 조건 슬롯을 런타임에 채워 쓰는 코드가
  있으면 그 자리에 다른 객체가 들어와 있을 수 있다. `CVariable`의 `Disabled(...)` 두 번째 액션은 실제
  액션이라 점유된다. 이런 사용처를 `CtrigAsm v5.5.lua`에서 전수 조사해야 한다.
- `PRT_SetInliningRate(0)`은 그대로 둔다(맵 자체 TRIG는 건드리지 않음).

효과는 3절 표의 "트리거 하나" 항목이 통째로 2.1절 값으로 바뀌는 것이다. 언어를 새로 만들지 않고
CtrigAsm 자산을 다 살리면서 얻는 가장 큰 단일 이득이다. 대신 어셈블러를 포크해 유지해야 하고,
Ninfia의 원본과 갈라진다.

## 6. 미검증·주의

- 2.1절 실측은 합성 트리거(같은 모양 100~200개)다. 실제 맵은 모양이 섞여 있어 겹침 효율이 다르다.
  액션 63개 트리거는 이 빌드의 할당기가 인덱스 범위 밖 패닉을 내서 재지 못했다.
- `EUDVariable` 실측 144바이트는 변수 버퍼의 구멍에 다른 객체가 들어가지 않은 경우다. 실제 맵에서는
  더 작다.
- epScript 대응표는 `epparser.lemon`의 문법 액션 기준이다. `static`, `once`류는 이 판에 없었다.
- 5절은 코드를 읽고 세운 설계이며 구현·검증하지 않았다.

## 7. 어셈블러 플러그인의 패치 규약과 제약 (실측, 2026-09-11)

5절의 "어셈블러 포크" 안을 판단하기 위해 `Py/STRCtrig Assembler v5.5.py`의 런타임 패치 루프와
theSeed 빌드 산출물(`~/seed-build/C:/euddraft0.9.2.0/Ctemp/TRIGP*.chk`)을 실측했다.

### 7.1 청크 형식과 보폭 — 2416바이트가 맞다

| 파일 | 크기 | 보폭 | 개수 | 형식 |
| --- | --- | --- | --- | --- |
| `TRIGP0.chk` | 595,200 | 2400 | 248 | CHK TRIG 형식. 플러그인 150~165행이 맵 TRIG 섹션 앞에 이어붙임 |
| `TRIGP1~7.chk` | 681,312 | 2416 | 282 | SC 메모리 노드 형식: prevptr 4 + nextptr 4 + TRIG 2400 + 여분 8 |
| `TRIGP8.chk` | **129,333,312** | 2416 | **53,532** | 같음. theSeed의 FP 코드 전부 |

`file_sizeX = file_size // 0x970`(439행), STRX PATCH 루프의 `CurEPD.AddNumber(604)` +
`SetMemory(0x6509B0, Add, 605)`(1936행, 루프 안의 `-1` 보정 포함)가 604 dword = 2416바이트 보폭이다.
`TRIGP0`는 게임이 로드한 트리거 노드 리스트를 `0x51A280 + 8 + 0xC*p`에서 시작해 **처음 3개만 next
포인터를 따라가고 그 뒤로는 `+0x970`씩 더한다**(340~350행). 게임이 노드를 연속 할당한다는 가정이다.

TEP 한도 65,536개 대비 theSeed P8 청크는 이미 82%다. 최종 `.scx`(`TheSeed_Test.scx`)는 MPQ 압축으로
1,063,254바이트지만, 게임 메모리에서는 STRx 섹션에 129MB가 그대로 풀린다.

### 7.2 트리거 하나마다 런타임에 하는 일 (STRX PATCH, 1802~1936행)

1. **Connect Next**: `nextptr`에 청크 base(ΔEPD)를 더한다. tepc는 nextptr을 상대값으로 써 둔다.
2. 조건 0의 type 바이트가 `0xFE`면 Label 트리거. 조건 15개, 액션 64개를 차례로 훑는다.
3. **조건 마커**: type 상위 니블 `0xF` → type을 `0x0F`(Deaths)로 바꾸고 player 필드에 base를 더한다.
   `0x800000` 비트가 STRx 청크 base인지 TRIG base인지, `0x0?000000` 니블이 P1~P8 중 어느 base인지 고른다.
4. **액션 마커**: type 바이트 `0xF8` → `0x2D`(SetDeaths)로 바꾸고 player 필드에 base. 값 필드 옆 플래그
   `0xF000`(Value EPD) / `0xE000`(Value PTR)이면 값에도 base(또는 base×4)를 더한다.
5. **Skip**: `prevptr` 하위 20비트가 N이면 뒤 N개는 데이터(CArray/CDb/문자열)라 훑지 않는다.
6. Label `0x1FFF0`은 NSQC용 특수 마커(`NSQCASM = CurEPD + 87 - 604*7`).

즉 이것은 **재배치 테이블을 런타임에 트리거로 실행하는 것**이다. eudplib이 `ConstExpr`로 컴파일 타임에
하는 일과 같다.

### 7.3 theSeed P8 청크의 실제 구성

| 항목 | 개수 | 비고 |
| --- | --- | --- |
| Label(`0xFE`) 트리거 | 46,027 | 86% |
| 재배치 대기 액션(type `0xF8`) | 334,821 | 트리거당 6.3개. 맵 시작 시 전부 패치 |
| Skip 데이터 트리거 | 7,248 (13.5%) | 헤더 1,564개. CArray/CDb/문자열 |
| 모양 (2,1) | 10,284 | `Label + 조건 1, 액션 1` — T/TT 마샬링 |
| (2,2) / (1,2) / (1,1) | 5,416 / 5,242 / 4,243 | `CVariable`(1,2 = 액션 + Disabled 액션) 포함 |
| (1,6) / (1,5) | 3,829 / 2,608 | 호출 규약 트리거 |
| (3,29) / (3,62) / (2,46) | 1,700 / 1,700 / 1,688 | `CunitCtrig` 1700슬롯 언롤 3벌 ≈ 12MB |
| (1,0) / (2,0) | 1,673 / 1,565 | 점프·구조 트리거 |

액션 5개 이하의 작은 트리거가 약 59%다. 2.1절 값으로 환산하면 이 부분은 2416 → 230~500바이트로
줄지만, Skip 데이터 7,248 × 2416 = 17.5MB와 `CunitCtrig` 언롤 12MB는 그대로다. 코드 트리거만 겹쳐
쌓았을 때 P8 청크는 **129MB → 대략 45MB(1/3)** 로 추정된다.

### 7.4 겹쳐 쌓기를 막는 제약 — 5절 안의 실제 조건

1. **보폭이 라이브러리에 박혀 있다.** `CtrigAsm v5.5.lua`에 `604`가 667회, `0x970`이 307회 등장한다.
   `VArr`/`VArrX`/`ConvertVArr`의 `index * 604`, `CallLabel`의 `Next = 1`(= 다음 트리거), `f_` 함수의
   `Ret` 슬롯, `NSQCASM + 87 - 604*7` 전부 "트리거 간격 = 2416"을 전제한다. 컴파일 타임 참조는 상수로
   치환할 수 있지만 **런타임 인덱스 산술이 걸린 블록(CVArray, CArray, 문자열)은 고정 보폭이어야 한다.**
2. **`CArray`/`CDb`는 이미 밀집 데이터다.** 트리거 하나에 602 dword를 담고(`Size/602`, 6694행) Skip
   헤더로 스캔을 건너뛴다. 4바이트/원소라 겹쳐 쌓을 것이 없다. 반면 `CVArray`는 원소 하나가 트리거
   하나(2416바이트)다.
3. **마커가 트리거 바이트 안에 있다.** 런타임 스캔이 2416바이트 전체를 읽으므로, 겹쳐 쌓으면 남의
   객체 바이트를 마커로 오인한다. 스캔을 컴파일 타임(플러그인이 파이썬으로 레코드 파싱)으로 옮겨야 한다.
4. **재배치가 맵 시작 시 실행된다.** 53,532개 × (nextptr + 조건 15 + 액션 64 검사) 규모라 로딩
   시간의 상당 부분이 여기다. 컴파일 타임 재배치로 바꾸면 이 비용은 0이 된다.
5. **플레이어별 청크 8개 + 맵 TRIG.** 참조에 플레이어 니블과 STRx 비트가 들어 있어 청크 간 참조는
   되지만 라벨 공간은 16비트(`Prohibited_Label = 0xFFE0` 이하)다.
6. `PRT_SetInliningRate(0)` 필수(2.8절). 맵 TRIG 쪽 eudplib 인라인·공유는 포기한다.
7. `TRIGP0` 워커의 "3개 뒤부터 `+0x970`" 가정(7.1절)은 게임 할당기에 의존한다.
8. 청크가 `Db` 하나라 eudplib의 스태킹·재배치·상수 접기가 전혀 개입하지 못한다.

### 7.5 그래서 5절 안은 어떻게 좁혀지는가

- **코드 트리거만** `RawTrigger(trigSection=rec[8:2408])`로 만들고, Skip 블록과 `CVArray` 블록은
  지금처럼 `Db`(고정 보폭)로 둔다. 코드 트리거의 마커는 플러그인이 파이썬에서 파싱해 `ConstExpr`
  (대상 트리거 EPD + 필드 오프셋)로 치환한다. `Next = 1` 참조는 "다음 레코드"로 정적으로 푼다.
- 코드 트리거에서 **런타임 인덱스로 다른 코드 트리거를 가리키는 곳**(예: `CallVariable`의 계산된
  Index, `Stage`, 점프 테이블류)은 보폭 가정이 있으므로 라이브러리 전수 조사 대상이다. 604 등장
  667곳 중 코드 트리거 간 산술만 골라내면 된다.
- 기대 효과: theSeed 기준 페이로드 약 1/3, 맵 시작 재배치 루프 제거. 트리거 **개수**(TEP 65,536
  한도)는 줄지 않는다. 개수를 줄이는 것은 4절의 새 언어(마샬링 트리거 자체가 없어짐)만이 한다.

| + jump | 52.0 MB | 0.402 | −5.0 MB |
| + cvar | **49.3 MB** | **0.381** | −2.7 MB |
| + varray (라이브러리 수정 가정) | 48.5 MB | 0.375 | −0.8 MB |
| + full | 50.4 MB | 0.390 | +1.9 MB (넣지 말 것) |

코드 42,137개는 101.8 MB → 22.6 MB(평균 2416 → 537 B)가 되고, 남는 49.3 MB의 구성은 데이터 블록
21.3 MB(43%), `full` 5.4 MB, 겹쳐 쌓인 코드 22.6 MB다. 종류를 하나만 단독으로 쌓으면 할당기가 앞으로만
채우는 성질 때문에 절감이 과소평가된다(예: marsh 단독 −29.7 MB 대 marsh_nocond 단독 −17.3 MB, 합산
67.9 MB < 누적 80.1 MB). 판단은 누적 표로 할 것.

**실험이 드러낸 것 두 가지 — 툴체인을 바꾸지 않아도 되는 절약**

1. **`CA2ArrX/Y/Z = f_GetVArrptr(FP,1700)` 3개가 12.3 MiB, 5,100개(TEP 한도의 7.8%)를 차지하는데
   theSeed 어디에서도 쓰지 않는다** (`Engine/G_CB_Lib.lua` 70~72행 선언뿐. `MSF_GaLaXy.R/func.lua`
   283~285행도 같은 선언). tepc의 STRCtrig 모드가 요청 트리거 하나를 1700개 빈 슬롯(각 2416 B, Label 마커
   23바이트만 있음)으로 펼친다. 선언을 지우면 즉시 사라진다. 지운 뒤 `TRIGP8.chk` 크기가 정확히
   5,103 × 2416 = 12,328,848 B 줄어야 한다.
2. **`UnitReadX` 2회 + `f_CGive` Include가 1700 언롤 3벌(5,089개, TEP 한도의 7.8%, 12.3 MiB)** 을 만든다.
   `(3,62)`짜리는 겹쳐 쌓아도 이득이 없다. 유닛 슬롯 순회를 언롤 대신 Cp 트릭 런타임 루프(`SetMemory(0x6509B0,
   Add, 84)` 반복)로 바꾸면 1700개가 수십 개가 된다. 이건 라이브러리 함수 교체이지 툴체인 변경이 아니다.

**결론: 종류별 절약 가능 범위**

- 겹쳐 쌓기(어셈블러 포크)로 줄어드는 것: 코드 트리거 42,137개. 129 MB → 49 MB.
- 겹쳐 쌓기로 안 줄어드는 것: Skip 데이터(21 MB), 60액션 이상(5 MB), 런타임 인덱싱 VArray(0.8 MB).
- 트리거 **개수**는 어느 경우에도 안 줄어든다. 개수를 줄이는 것은 (a) 미사용 배열 삭제 −5,103, (b) 1700
  언롤 → 런타임 루프 −5,000 안팎, (c) 마샬링 27,657개(52%)를 없애는 VProc/SeqCompute식 방출(새 언어 또는
  라이브러리 v6)뿐이다.

### 7.7 검토: 겹쳐 쌓은 트리거의 "다음 부분"을 게임이 추가 액션으로 오인할 수 있는가

두 층으로 나눠 봐야 한다. **게임 엔진이 읽는 것**과 **CtrigAsm이 런타임에 고쳐 쓰는 것**이다.

#### (1) 엔진 쪽 — 설계상 안전하다

- 트리거 엔진은 조건 16개·액션 64개를 앞에서부터 훑다가 **type 바이트가 0(None)인 항목을 만나면 멈춘다.**
  BWAPI `BW/TriggerEngine.cpp` 13~36행이 이 규약을 그대로 옮겨 놓았다("None also indicates the end of
  the list"). 그 뒤 슬롯에 무엇이 있든 읽지 않는다.
- eudplib 할당기(`rust/src/allocator/pbuffer.rs` `_write_trigger`)는 사용한 조건 뒤에 **0으로 채운 조건
  20바이트**, 사용한 액션 뒤에 **0으로 채운 액션 32바이트**를 항상 쓰고, 점유 지도(`payload.rs`
  `_write_trigger`)에서 그 종료 표시(조건 5 dword, 액션 8 dword)를 **점유로 표시**한다. 다른 객체는
  그 자리에 들어올 수 없다. prevptr·nextptr, 플래그 dword(+2376), 마지막 dword(+2404, `currentAction`
  바이트 포함)도 점유다. 조건 16개·액션 64개를 다 쓴 트리거는 종료 표시가 없지만 엔진이 개수 한도에서
  멈춘다.
- 비점유로 남는 곳은 종료 표시 **뒤**의 조건·액션 슬롯과 플레이어 바이트 27개뿐이다. 앞의 것은 엔진이
  읽지 않고, 뒤의 것은 TRIG 로드 시 플레이어 리스트를 만들 때만 쓰이며 nextptr로 연결된 페이로드
  트리거에서는 참조되지 않는다.
- CtrigAsm의 `Label` 마커 조건은 type `0xFE`에 플래그 `0x02`(`TriggerEntryFlags::IgnoreExecution`,
  BWAPI `Triggers.h` 110행)라 엔진이 건너뛴다. 남겨 두어도 무해하고, 지우면 20바이트 준다.
- 경험적 근거: eudplib은 `CompressPayload`(이 겹쳐 쌓기)를 기본으로 켜고 수년간 배포 맵을 만들어 왔다
  (0.80.6은 끄는 옵션 자체가 "not supported"다).

즉 **"게임이 이웃 바이트를 액션으로 오인해 실행하는" 일은 종료 표시가 살아 있는 한 일어나지 않는다.**
관건은 그 종료 표시를 누가 지우느냐다.

#### (2) CtrigAsm 쪽 — 종료 표시 뒤의 빈 슬롯을 저장소로 쓰는 곳이 있다

theSeed P8 청크의 정적 참조 373,427건(조건 `0xF8` player, 액션 `0xF8` player, 값-EPD 플래그 `0xF?`)을
전부 풀어 대상 필드가 겹쳐 쌓기 후 점유 범위 안에 있는지 셌다(도구 `hazard` 모드).

| 항목 | 건수 |
| --- | --- |
| 정적 참조 전체 | 373,427 |
| 겹쳐 쌓기 후 **비점유** 슬롯을 읽거나 쓰는 참조 | **2,194 (0.6%)** |
| 종료 슬롯 또는 그 뒤에 **type 바이트를 쓰는** 참조 | **29** |
| 그 참조들이 향하는 대상 트리거 | **7개** |

7개의 정체:

있다. 지금은 2416바이트 안에 슬롯이 물리적으로 있어서 문제가 없다.

#### (3) 규칙 — 무엇을 겹쳐 쌓으면 안 되는가

1. **정적으로 잡히는 것**: 다른 트리거가 자기 점유 범위 밖 슬롯을 읽거나 쓰는 대상 트리거는 2416바이트
   `Db`로 고정한다. 도구가 자동 검출하고 `stack` 모드가 이를 `pinned`로 제외한다. theSeed에서는 7개,
   비용 17KB. 결과 49.34MB로 7.6절과 사실상 같다.
2. **정적으로 안 잡히는 것**: 인덱스를 런타임에 계산해 닿는 영역은 청크 바이트만 봐서는 모른다.
   `CVArray`/`CreateVArr`(`*604`), `__SetCAPlotJumpAlloc`/`__SetCAPlotVarAlloc` 범위, `CStack`/`LStack`,
   `NSQCVArray`, `FlagAlloc` 범위. 이들은 Lua 쪽이 범위를 알고 있으므로 **tepc/Lua가 "고정 보폭 범위
   목록"을 내보내고 플러그인이 그 범위를 통째로 `Db`로 두는** 규약이 필요하다. 7.4절 1번 항목의 실체가
   이것이다.
3. **종료 표시는 절대 건드리지 않는다는 보장이 필요하다.** 위 (2)의 29건이 그 예외인데 전부 1번 규칙의
   7개 안에 있다. 새 라이브러리 함수를 추가할 때 "빈 슬롯을 저장소로 쓰지 않는다"를 규칙으로 못 박아야
   한다. 저장소가 필요하면 `CArray`(데이터 블록)나 전용 변수 트리거를 쓰고 그 트리거를 고정 목록에
   올린다.
4. **`Wait` 액션이 있는 트리거**는 `currentAction` 바이트로 재개 위치를 기억한다. 그 바이트는 점유
   범위 안이라 안전하지만, 재개 인덱스는 자기 액션 범위 안이어야 한다. 겹쳐 쌓기와 무관하게 성립한다.

결론: 엔진은 오인하지 않는다. 오인을 만드는 것은 CtrigAsm이 빈 슬롯을 저장소·코드 생성 공간으로 쓰는
관행이며, theSeed 기준 그 영향 범위는 트리거 7개로 정적 검출된다. 런타임 계산 범위만 Lua가 알려 주면
나머지는 기계적으로 안전하게 처리할 수 있다.

### 7.7 안전성: 겹쳐 쌓은 트리거의 "다음 바이트"를 게임이 액션으로 오인하는가

**실행기의 규칙.** 게임의 트리거 실행기는 조건 16개·액션 64개를 순서대로 보다가 **type 바이트가 0인 항목을
만나면 거기서 멈춘다**(BWAPI `BW/TriggerEngine.cpp` 13~21행, 28~36행이 같은 규칙으로 모델링한다). eudplib은
이 규칙에 기대어 마지막 조건 뒤 20바이트, 마지막 액션 뒤 32바이트의 **종료 표시 슬롯을 통째로 점유**로
잡는다(`pbuffer.rs` `_write_trigger`: 조건 뒤 5dword, 액션 뒤 8dword `push(true)`). 그래서 종료 표시
뒤에 남의 객체가 와도 실행기는 읽지 않는다. 이 규칙이 틀리다면 eudplib의 72바이트 변수 버퍼(다음 변수의
액션이 33개 앞 트리거의 액션 영역 안에 겹쳐 있음)가 모든 맵에서 깨졌을 것이다. 즉 **정적인 트리거는 안전하다.**

**위험은 런타임 쓰기다.** 세 가지 경우만 문제가 된다.

1. 종료 표시 슬롯의 **type 바이트에 0이 아닌 값**을 쓰는 경우. 그러면 실행기가 그 슬롯을 실행하고 다음
   슬롯(겹쳐 쌓기에서는 남의 바이트)을 읽는다. theSeed P8 청크에서 종료 표시 dword를 쓰는 참조는 10건이고
   **전부 type 바이트에 0을 쓴다**(cond 5건: 값 0x1/0xA = 비교자 필드, act 5건: 값 0x0/0x1 = unit 필드).
   지금은 없지만 값이 0x10000 이상이 되는 순간 위험해지는 잠재 구조다.
2. 종료 표시 **뒤**(죽은 공간)를 저장소로 쓰는 경우. 실행은 안 되지만, 겹쳐 쌓으면 그 자리에 있는 남의
   객체를 덮어쓰고 남의 객체가 그 값을 덮어쓴다. **CtrigAsm은 이것을 체계적으로 한다.**
   `CDeaths`/`SetCDeaths`/`NDeaths`/`FlagIndex`가 `0x1C8 + 4*Line`(액션 4번 슬롯부터 480줄)을 플래그·카운터
   저장소로 쓰고, `CWhile`/`CLoop`은 자기 구조 트리거의 `Ccode(IndexAlloc+1, 0)`에 반복 횟수를 둔다.
   1700 언롤 루프(`UnitReadX`, `f_CGive`)는 대상 트리거의 line 342(`act46+24`)를 20만 번 쓴다.
3. 조건/액션 슬롯을 런타임에 **새로 만들어 넣는** 경우(마커 0xF8이 아닌 실제 type 값을 쓰기). theSeed에서는
   1번의 10건 외에 발견되지 않았다.

**theSeed 실측** (`trigp_stackexp.py audit`, 청크 내부 양수 참조만):

| 항목 | 값 |
| --- | --- |
| 죽은 공간을 참조당하는 트리거 | 21,739개 (전체의 41%) |
| 그중 코드 종류 | 18,496개 (코드 42,137개의 44%) — marsh 5,684 / marsh_nocond 6,147 / logic 4,362 / mixed 1,702 / jump 599 |
| 그중 홀더(100건 이상 참조) | 233개 — Ccode/Ncode/플래그 홀더(`CVariable(AllPlayers, CreateCCodeVarXAlloc+k)`, `Label`만 있는 (1,0)) |
| 히트가 몰린 줄 | line 342: 201,894 / 256: 22,080 / 341: 11,159 |
| 종료 표시 type 바이트를 덮는 쓰기 | 10건, 전부 0 기록 |
| 청크 밖(음수 상대 EPD) 참조 | 23,019건 — 기준점 미해독. 이 중 일부가 실제로는 P8 안을 가리킨다면 위 집합은 더 커진다 |
| 도구 `audit` 모드 값 (P8 내부 소스만, P0 제외) | 20,586개 / 홀더 227 / type 바이트 쓰기 4건 / `safe` 0.699 (90.4 MB) |

위 표의 21,739개·10건·0.719는 `TRIGP0.chk`(맵 TRIG)에서 P8로 들어오는 참조까지 포함한 값이다.

**결과: 안전 집합만 겹쳐 쌓으면 129.3 MB → 93.0 MB (0.719)** 다. 7.6절의 0.381은 죽은 공간 사용을 무시한
상한이었다. 두 값의 차이 44 MB가 "CtrigAsm의 저장 규약" 때문에 못 얻는 몫이다.

**0.38로 돌아가려면** 라이브러리의 저장 규약을 바꿔야 한다. 트리거 죽은 공간 대신 전용 데이터 블록(`Db`나
eudplib `EUDArray`)에 Ccode/Ncode/플래그/루프 카운터를 두면 되고, 바꿀 곳은 `CDeaths`·`SetCDeaths`·
`CDeathsX`·`NDeaths`·`FlagIndex`·`Ccode` 사용처(`CWhile`/`CLoop`/`NLoop` 계열의 `Ccode(IndexAlloc+n, 0)`)와
1700 언롤 함수들이다. `0x1C8` 상수를 쓰는 함수는 소수지만 호출처가 많으므로, 바꾼 뒤 `audit`가 0에 가까워지는지로
검증한다. 이 변경은 겹쳐 쌓기와 무관하게도 이롭다. 죽은 공간 값이 0x10000을 넘으면 액션 type 바이트가
오염되는 1번 위험이 사라진다.

**정리.** "다음 바이트를 추가 액션으로 오인"은 종료 표시가 지켜지는 한 일어나지 않는다. 일어나는 것은
"죽은 공간을 저장소로 쓰는 코드와 그 자리를 차지한 남의 객체가 서로를 덮어쓰는" 손상이며, theSeed 코드
트리거의 44%가 그 저장소를 가지고 있다. 따라서 어셈블러 포크의 순서는 (1) `audit`가 가리키는 트리거를 `Db`로
남기는 안전 모드(0.72), (2) 저장 규약 변경 후 전면 겹쳐 쌓기(0.38)다.
