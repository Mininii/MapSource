# SNQC 변경 기록

판(edition)마다 따로 번호를 붙인다. 두 판은 설계가 같아도 코드가 달라서 고친 곳이 다르다.

| 판 | 파일 | 번호 자리 | 지금 |
| --- | --- | --- | --- |
| euddraft 플러그인 판 | `SNQC.py` | `SNQC_VERSION` (빌드 로그 `[SNQC 1.1] map ...` 에 찍힌다) | 1.1 |
| CtrigAsm 판 | `SNQC.lua` | `SNQC_Version` | 1.2 |

## 쓰는 법

- 판을 고치면 그 판의 **다음 판** 단락에 한 줄씩 적고, 같은 커밋에 넣는다.
- 번호를 올릴 때 파일 안의 번호 자리도 같이 바꾼다.
- 분류: **추가** / **변경** / **수정** / **확인** (해당하는 것만). "확인" 은 코드 변경 없이 실제 환경에서 검증한 것.
- 실측 과정과 근거는 `HISTORY.md`, 설계는 `DESIGN.md` 에 둔다. 여기에는 판마다 무엇이 달라졌는지만 적는다.

## CtrigAsm 판 (`SNQC.lua`)

### 1.2 — 2026-09-17 (MSF_UE_RE 인게임 시험 반영)

**수정**

- **채널 건물의 유닛 ID 가 16비트를 넘어 패킷이 깨졌다.** CtrigAsm 의 `f_EPDToAlphaID` 는 세대 바이트(CUnit+0xA5)
  전체에 2048 을 곱한다. 게임은 세대를 32 로 나눈 나머지로 비교하므로(OpenBW `get_unit`) 세대가 32 이상인 칸에
  만들어진 채널은 ID 가 16비트를 넘고, 넘친 비트가 패킷 머리 `01 A A 15` 의 명령 바이트(0x15)를 바꿨다.
  그 채널은 아무것도 못 받고, 같은 턴의 뒤따르는 명령까지 잘못 읽힐 수 있었다.
  유닛이 자주 생기고 없어지는 맵일수록 세대가 빨리 올라서, 채널마다·판마다 결과가 달랐다.
  - 증상 (MSF_UE_RE): 키 입력은 되는데 SCR_DB 불러오기가 워드 10~15개에서 멈춤 (예전 MSQC 빌드는 0.3~1초).
  - 고침: ID 를 직접 계산한다 = 인덱스 + 1 + (세대 mod 32) × 2048. 선택 되돌리기의 원래 선택 ID 도 같은 함수로.
    (플러그인 판·MSQC 는 세대를 0 으로 고정해서 이 문제가 없었다. 여기서는 세대를 건드리지 않는다.)
  - 곁들여 `f_EPDToAlphaID` 가 마지막 칸(인덱스 1699)에서 0 을 내던 것도 피한다.
- **한 턴의 4·8번째 패킷이 늘 사라졌다.** CtrigAsm v5.5 `f_Memcpy` 의 "대상 주소 4의 배수 / 원본 4로 나눠 2·3 남음" 경로는
  끝자투리 바이트 마스크에 오타(`0x00FFFF000`, `0x00FF00000`)가 있다. SNQC 패킷은 15바이트를 PB+3 에서 복사하므로
  턴 버퍼 시작 위치(7 + 15k)가 4의 배수인 패킷의 끝 3바이트(오더 0x28)가 깨져 랠리 명령이 되지 않았다.
  - 증상 (MSF_UE_RE): 불러오기 72초. 채널을 동시에 여러 개 보낼 때만, 앞선 줄 수에 따라 판마다 다른 SCR_DB 채널이 죽음.
    게임 중 메모리 시험으로 "4·8번째 패킷만 사라짐" 을 재현했다 (혼자 보내면 모든 채널·값이 들어감).
  - 고침: SNQC 안에 **고친 복사 함수(`Call_Copy`)** 를 두고 `f_Memcpy` 를 더 쓰지 않는다 (패킷, 선택 되돌리기, 합치기 읽기/쓰기, 채널 선택 풀기).
    f_Memcpy 와 같은 방식(4바이트씩 + 자투리)이지만 정렬 16가지 경우의 마스크·배수를 손으로 쓰지 않고
    "원본 바이트 위치 → 대상 바이트 위치" 에서 계산해 만든다. 파이썬 모의 실행(정렬 16가지 × 길이 0~40, 3000회)에서
    정확히 N바이트만 옮김을 확인. CtrigAsm 원본 파일은 고치지 않았다 (다른 맵이 같이 쓴다).
  - (중간 판) 처음에는 복사 길이를 4의 배수로 올려(16 / 28바이트) 그 경로만 피했다 - 인게임 0.4초 확인은 이 판에서 했다.

**추가**

- 고친 복사 함수 `Call_Copy` (위 수정 항목).
- `PlayerXY = {[플레이어] = {x, y}}` - 플레이어별 첫 채널 자리. `Columns = n` - 한 줄에 놓을 채널 수 (격자로 접기).
  채널 건물은 시야 0 이어도 자기 칸 주변을 밝히고(주인이 사람이라 끌 수 없음) 시야 공유로 남에게도 보여서,
  플레이어가 원래 보는 곳(예: 자기 배럭 밑)에 두려는 것. 채널 자리가 겹치면 컴파일을 멈춘다. `Step` 은 32 이상만.
- `DebugAddr` (시험용) - 매 사이클 이 PC 의 채널 상태(EPD, ID, 보낸·고친·받은 수, 마지막 받은 값, 건물의 종류·주인·오더·상태·랠리·좌표·세대)를
  그 주소에 복사한다. `MSF_UE_RE/tools/snqc_probe.py` 가 게임 중에 읽는다.

**확인**

- 가짜 CtrigAsm 환경, MSF_UE_RE 빌드.
- 인게임 (1.2 첫 빌드): 불러오기 72.6초 → 위 f_Memcpy 문제로 확인.
- **인게임 (길이를 4의 배수로 올린 중간 판, MSF_UE_RE 싱글)**: SCR_DB 불러오기 0.4초 (항목 6개). 게임 중 메모리 시험으로 8채널 동시 전송 5회·3채널 3회 모두 도착.
- `Call_Copy` 판: 가짜 환경, 복사 모의 실행, MSF_UE_RE 빌드. **인게임 재확인 전.**

### 1.1 — 2026-09-17 (MSF_UE_RE 적용)

마린키우기 UnLimit ExceeD RE(MSF_UE_RE)에 처음 적용하면서 실제 tepc 컴파일에서 드러난 문제를 고쳤다.

**수정**

- **CtrigAsm 인덱스 초과로 컴파일 실패.** 1.0 은 (플레이어 × 채널 × 비트)마다 `CIf` 를 펼쳐서
  16채널 × 7명에서 인덱스(0xC000~0xEFFF)를 **6990개** 썼다 → `EndCtrig` 에서 `IndexAllocation_Overflow`.
  반복되는 본체(채널 만들기·살았는지 보기·랠리 칸 읽기·값/좌표 풀기·보내기)를 `SetCall` 함수로 한 번만 두고,
  펼치는 부분은 인덱스를 안 쓰는 `CTrigger` / `CallTriggerX` 로 바꿨다. 같은 크기에서 **112개** (tepc 실측).
- **보내는 쪽의 `Deaths(CurrentPlayer, ...)` 조건이 이 PC 플레이어를 보지 않았다.** 보내는 트리거는 FP 소유라
  CurrentPlayer 가 FP 다 (MSQC 는 보내기 전에 CurrentPlayer 를 로컬 플레이어로 바꾼다). MSQC 줄 문법의
  `Deaths(CurrentPlayer, 비교, 값, 유닛)` 을 이 PC 플레이어의 데스값 사본으로 바꿔 읽는다.
  그 밖에 CurrentPlayer 가 든 문자열 조건은 조용히 틀리지 않게 에러로 멈춘다.
- **MSQC 줄의 `mouse : 로케이션` 번호가 하나 밀렸다.** MSQC 는 로케이션 이름·번호를 1부터 세는데 0부터로 넘겼다.
  이름(`Location74` 등)도 못 읽었다. 둘 다 받고 1 을 빼서 넘긴다.
- **작업 공간이 지워지면 패킷이 깨졌다.** 패킷 틀의 고정 바이트를 게임 시작 때 한 번만 썼다. 맵이 그 자리를
  지우면(MSF_UE_RE 는 게임 시작 3초에 0x58F448~0x5967E8 을 비운다) 이후 명령이 잘못 나간다. 매 사이클 다시 쓴다.
- **채널 건물을 못 만들었는데 만든 것으로 볼 수 있었다.** 만들기 전후로 빈 유닛 포인터(0x628438)가 움직였는지도 본다.
- **죽은 채널 건물을 살아 있는 것으로 봤다.** 살았는지 볼 때 종류·주인 말고 오더 바이트(+0x4D, 0 = 죽는 중)도 본다.
- 만들 때 로케이션의 고도 플래그를 끄고, 이름·플래그 칸까지 되돌린다 (플러그인 판·MSQC 와 같게).
- units.dat 바이트 패치의 `256 ^ n` 이 Lua 5.3 에서 실수가 되던 것을 정수로.
- 키·마우스 눌림 기억 트리거를 `pairs` 순서로 내서 빌드마다 순서가 달라지던 것을 등록 순서로.

**추가**

- `SNQC_MyDeaths(비교, 값, 유닛)` 조건 - 이 PC 플레이어의 데스값.
- `SNQC_Version`.

**변경**

- 선택 되돌리기에 쓰는 원래 선택을 사이클 시작이 아니라 **새로 붙였을 때만** 읽는다 (보낼 것이 없는 사이클의 일을 줄임).
- 채널마다의 패킷 머리를 채널 건물을 만들 때 한 번 계산해 둔다 (공유 변수).
- 필요한 것이 늘었다: `MapSource/Library/LibraryFor322.lua` 의 `SetCall` / `CallTrigger(X)` / `def_sIndex`.
  `Include_CtrigPlib` 뒤에서 `SNQC_Install` 을 불러야 한다 (`f_Read` 가 요구한다).

**확인**

- 가짜 CtrigAsm 환경 실행 (`tests/stub_test.lua`, LuaLS 실행 파일의 Lua 5.5): 44줄 설치, 1.1 조건들, 인덱스 어림.
- MSF_UE_RE 실제 빌드 (tepc 2026-09-05 판 → euddraft → CPLP) 통과. 16채널 × 7명.
- **인게임은 아직.** DESIGN.md "확인 목록" 8번.

### 1.0 — 2026-09-17

- 첫 판. 플러그인 판과 같은 설계를 CtrigAsm 으로. Lua 함수 설정(`SNQC_Config`, `SNQC_Key`, `SNQC_Value`,
  `SNQC_Point`, `SNQC_Mouse`)과 MSQC 줄 문법(`SNQC_Line`).
- 플러그인 판에 없는 것: 값 유지(`Hold`), 새 값 표시(`NewDeath`), 바뀐 값만 보내기(`Change`), 작업 공간 주소(`WorkAddr`).
- 확인: luac 문법 검사와 가짜 CtrigAsm 환경 실행까지. 실제 TEP 컴파일은 안 했다 (1.1 에서 위 문제들이 나왔다).

## euddraft 플러그인 판 (`SNQC.py`)

### 1.1 — 2026-09-17 (채널 자리 설정)

**수정**

- **보내는 쪽 조건의 CurrentPlayer 를 이 PC 플레이어로 두지 않았다 → EUD 오류.** MSQC 는 보내기 전에
  `f_setcurpl(f_getuserplayerid())` 를 하는데 1.0 은 빠졌다. `Deaths(CurrentPlayer, ...)` 줄이 앞 트리거가 남긴 CP 로 읽혔고,
  CtrigAsm 맵은 CP 에 트리거 메모리 EPD 를 남기므로 엉뚱한 주소를 읽었다.
  - 증상 (MSF_UE_RE): 게임 시작 2프레임째 `EUD ERROR 0xDB8455A7` / `0xDB847707` (주소 0x247BAA58 / 0x247B88F8).
    채널 자리와 무관(기본 자리 빌드도 같음), MSQC 빌드는 정상. 두 주소 차이(0x2160)가 두 빌드의 STRx 크기 차이와 같아
    "맵 데이터 크기에 따라 바뀌는 값" 을 좇았고, 역산한 CP 가 0x908xxxx (CtrigAsm 트리거 EPD) 였다.
  - theSeed 줄에는 CurrentPlayer 조건이 없어 1.0 시험에서 드러나지 않았다. Lua 판 1.1 이 고친 것과 같은 종류.

**추가**

- `SNQC_XY1` ~ `SNQC_XY8 = x, y` - 플레이어 P1~P8 의 첫 채널 자리. 하나라도 주면 사람 슬롯 전부 줘야 하고 `SNQC_XY` 대신 쓴다.
- `SNQCColumns = n` - 한 줄에 놓을 채널 수 (0 = 한 줄). 넘치면 y 로 32 씩 다음 줄.
  - 까닭: 채널 건물은 시야 0 이어도 자기 칸 주변을 밝히고(유닛 주인이 사람이라 끌 수 없음) 플레이어끼리 시야를 공유하면
    남에게도 보인다 (MSF_UE_RE 시험에서 미니맵 오른쪽에 점). 플레이어가 원래 보는 곳(예: 자기 배럭 밑)에 두려는 것.
    Lua 판 1.2 의 `PlayerXY` / `Columns` 와 같은 뜻.
- 채널 자리가 겹치거나 맵 가장자리(16 미만)에 붙으면 컴파일을 멈춘다.

**변경**

- `SNQC_XY` 방식(플레이어별 자리를 안 줬을 때)도 `SNQCColumns` 를 따라 줄을 접는다. 기본값에서는 예전과 같다.

**확인**

- MSF_UE_RE `QCInput_Plugin = "SNQC_PY"` 빌드 통과 (euddraft·CPLP, `[SNQC 1.1]` 로그). CP 수정 전 빌드는 위 EUD 오류.
- **DPS강화하기 인게임 정상** (2026-09-17, 제작자 확인). MSF_UE_RE 의 CP 수정 뒤 인게임은 아직.

### 1.0 — 2026-09-17

- 첫 판. MSQC.py 의 설정 해석부를 가져와 줄 문법을 맞추고, 전송 채널을 가린 커맨드센터의 랠리 좌표로 바꿨다.
  채널 건물 생성·다시 만들기(`QCDebug`), 맵 크기에 맞춘 키 비트 배치, 합치기(`SNQCMerge`), 선택 되돌리기,
  `QCUnit` 이 랠리를 못 받는 종류면 106 으로 대신 쓰기.
- (같은 날 덧붙임) 판 번호 자리 `SNQC_VERSION` 을 만들고 빌드 로그에 찍는다 (`[SNQC 1.0] map ...`). 동작 변경은 없다.
- **확인**: theSeed 싱글·LAN 2인(64비트 + 32비트) 인게임 - 150프레임 소실 없음, 디싱크 없음, 선택 꼬임 없음.
  MSF_UE_RE 에서 `QCInput_Plugin = "SNQC_PY"` 로 euddraft·CPLP 빌드 통과 (2026-09-17, 인게임은 아직).
